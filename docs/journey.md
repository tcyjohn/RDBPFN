## 1. The Problem

### 1.1 Background

RDBPFN generates synthetic relational databases for pre-training a foundation model.
Each table has 12 `feature_N` columns generated by `MLPSCM`. The old code simply:

```python
feature_j = outputs_flat[random_index]  # one random MLP hidden unit per column
```

This produces features with **no shared structure** — each of the 12 features is an
independent draw from the MLP's flattened hidden states. The result:

| Metric | Synthetic (old) | Real Tab | Real Rel |
|--------|:---------:|:--------:|:--------:|
| avg \|corr\| p50 | 0.077 | 0.128 | 0.185 |
| feature var p50 | 2.04 | 14.15 | 76.21 |

The synthetic features have almost no pairwise correlation and very low variance.
Real data has substantially richer column structure — features covary because they
share underlying latent factors.

### 1.2 Design Philosophy

The HSBM FK generation uses a hierarchical stochastic block model to induce `FK`
correlation via shared cluster paths. The signal-group approach mirrors this:

- **HSBM (FK)**: latent hierarchy → block assignment → FK correlation
- **Signal Groups (features)**: latent signal sources → group assignment → feature correlation

Instead of one random unit per column, each feature is a linear combination of a
few **signal-group projections**, with features sharing the same group/basis
getting identical (up to magnitude) projection terms.

## 2. Architecture Overview

### 2.1 Signal Groups

Three signal groups, corresponding to the three sources of variation in a table:

| Group | Signal Dim | Source | Basis Dim (K) |
|-------|:----------:|--------|:-------------:|
| `time` | 8 + 3 | Fourier basis + Dirichlet gate from `_prepare_time_features()` | min(3, max(1, ⌈8/div⌉)) |
| `parent` | 12 | Per-edge FK projection of parent CAUSAL_OUTPUT | min(3, max(1, ⌈12/div⌉)) |
| `path` | 8 | Per-edge PathEncoder embedding of HSBM block path | min(3, max(1, ⌈8/div⌉)) |

### 2.2 Feature Construction Formula

For each feature _j_:

```
x_j = Σ_{g ∈ assigned_groups(j)} sign_{j,g} · |loading|_{j,g} · (signal_g @ B_g_basis[k])  +  ε_j
```

where:
- `sign ∈ {−1, +1}` (per basis, shared across features using the same basis)
- `|loading| ~ LogNormal(μ, σ)` — avoids Normal(0,σ) collapse to zero
- `B_g_basis[k]` is the k-th basis vector for group g (unit-norm)
- `ε_j ~ N(0, σ²_res)` — per-feature independent noise (NOT a group)

### 2.3 Data Flow

```
RDB.init_table_SCMs(seed)
  ├─ HpSampler: per-table HPs (group_scale_*, loading_*, coupling_lambda, …)
  ├─ HSBM HPs per parent: num_levels, clusters_per_level
  ├─ compute_hsbm_locality(hierarchies) → structural proxy
  ├─ classify_archetype → base_α → perturb → final_α
  │
  └─ MLPSCM.__init__(archetype_params, relation_keys, parent_causal_dims, …)
       ├─ _sample_feature_groups(α, 12) → per-feature: (group, basis_idx, sign, loading)
       ├─ _init_group_bases() → subspace-split orthonormal basis vectors
       ├─ _init_parent_projectors() → nn.ModuleDict[RelationKey] = Linear(D_causal→12)
       ├─ _init_path_encoders() → nn.ModuleDict[RelationKey] = PathEncoder(L_p, …)
       └─ _init_cross_feature_coupling() → uniform off-diagonal W matrix

TableGenerator.generate_data()
  ├─ _compute_hsbm_fk_ids() → (fk_ids, block_paths)
  └─ MLPSCM.forward_with_input(parent_data_list, fk_ids, block_paths)
       ├─ [existing] MLP forward → CAUSAL_OUTPUT, FULL
       ├─ _build_time_signal() → (seq_len, 11)
       ├─ _build_parent_signal() → per-edge project → mean-pool → (seq_len, 12)
       ├─ _build_path_signal() → per-edge embed → mean-pool → (seq_len, 8)
       ├─ _normalize_signals() → group-specific RMS/gates-ASIS
       ├─ _construct_features() → X(seq_len, 12)
       └─ _apply_cross_feature_coupling() → X += λ · X @ W
```

## 3. Contracts and Phases (Implementation)

### 3.1 Phase 0: Contracts (NO business logic)

- **RelationKey**: `namedtuple("RelationKey", ["child_table", "fk_col_idx", "parent_table"])` with factory `make_relation_key()`
- **TIME_BASIS_DIMS** = (0, 8), **TIME_GATE_DIMS** = (8, 11) — hard signal split
- **FEATURE_GEN_MODE_ACTIVE_HPS** — gates which HPs are active per mode
- **12 stub methods** on MLPSCM: `_classify_archetype`, `_compute_base_alpha`, `_perturb_alpha`, `_sample_feature_groups`, `_init_group_bases`, `_init_parent_projectors`, `_init_path_encoders`, `_build_time_signal`, `_build_parent_signal`, `_build_path_signal`, `_normalize_signals`, `_construct_features`
- **PathEncoder(nn.Module)**: per-edge `Embedding(L_p, max_block, 4) → Linear(L_p×4 → 8)`

### 3.2 Phase 1: State Initialization

Archetype → α mapping:
- Source tables (no FK parents): α = [1.0, 0, 0] (time only)
- Dependent non-timestamp: α = [0.1, 0.55, 0.35]
- Timestamp dependent: α = [0.5, 0.25, 0.25]
- Multi-parent (≥2 parents): inflate parent share, capped at 0.6
- Perturbation: `α_g *= exp(N(0, σ²_archetype))`, re-normalize

Per-feature assignment:
- Dirichlet(α_final) → group weights → top-K groups (max_groups_per_feature)
- Round-robin basis index allocation (ensures uniform sharing across features)
- Shared sign per (group, basis_idx) — features with the same basis get the same sign
- Independent LogNormal loading magnitude per feature

### 3.3 Phase 2: HSBM + Path Encoder

- `compute_hsbm_fk_ids()` → `(fk_ids, block_paths)` — now returns cluster path per child row
- `compute_hsbm_fk_ids_multi()` → `(fk_ids, cluster_b)` — shared latent cluster path
- `_build_path_signal()`: block_paths prefix → PathEncoder per edge → mean-pool
- Fallback: `block_paths=None` → `path_signal = zeros` (graceful degradation)

### 3.4 Phase 3: Signal Generators + Normalization

- `_build_time_signal()`: returns cached `_prepare_time_features()` output (basis 0:8 + gates 8:11)
- `_build_parent_signal()`: per-edge `Linear(D_causal → 12)` on parent rows via `fk_ids[:, i]` → mean-pool
- `_normalize_signals()`: time_basis → RMS÷_×scale, time_gates → AS-IS, parent/path → RMS÷_×scale

### 3.5 Phase 4: Feature Construction + Gate

- `_construct_features(signals, residual_sigma)`: iterates pre-assigned groups/bases, computes `proj = signal @ B[k]`, adds `sign × magnitude × proj + ε_j`
- `_apply_cross_feature_coupling(X)`: `X_out = X + λ · (X @ W)` where W is uniform off-diagonal
- Gate: `if self.use_signal_group_features: … else: <old parent_injection_scale path>`
- Both `forward_with_input()` and `forward_without_input()` wired

### 3.6 Phase 5: Verification

- 20/20 RDB smoke test: 0 errors
- `use_complex_tasks=False`: 2/2, OK
- `use_signal_group_features=False` → old path works, byte-identical output

### 4.6 P1 — Low-Rank Cross-Feature Coupling Layer

**Design**: `X_out = X_struct + λ · (X_struct @ U @ V^T)` where rank(U·V^T) = 2-3.

**Iterations**:
1. Column-normalized W: correlation erratic (λ=0.02 gave 0.91, λ=0.04 gave 0.54)
2. Zero-diagonal + column-normalized: still highly λ-sensitive
3. Inter-family-weighted W (2× cross-family, 0.5× intra-family): moderate improvement
4. Uniform off-diagonal W: simplest, most predictable

**Result**: P1 alone (λ∈[0.02,0.12]) gave corr 0.051 — same as v5. The coupling was too weak
at the λ values being sampled.

### 4.7 P2 — Correlated Basis Families (Continuum Model)

**Design**: `b_k = ρ_k · p₀ + √(1-ρ_k²) · ε_k` with descending ρ_k anchored to a global prototype.

**Results**:
- With K=2 + continuum (ρ=0.7→0.3): corr = 0.47, top5/total = 0.99, entropy = 0.31
  **Too concentrated** — the shared prototype made ALL basis vectors correlate.
- The design hypothesis ("少数主因子 + 长尾" in real data) was WRONG for rel-event.
  Real data has entropy=0.92 (very flat), not concentrated.

**Discovery**: Even with independent (orthogonal) basis vectors, the TIME SIGNAL itself
has structured covariance. The Fourier basis functions are mathematically correlated,
making `signal @ B[0]` and `signal @ B[1]` correlated even if `B[0] ⟂ B[1]`.

### 4.8 v6-v7 — Subspace-Split Orthogonal Bases

**Design**: Each group's signal is split into K disjoint subspaces. Basis k projects only from
subspace k, guaranteeing zero shared signal between different bases. Cross-basis correlation
is then controlled SOLELY by the coupling layer λ.

**v6** (K=2, λ∈[0, 0.12]):
- Aggregate corr: 0.36 — still too high. With K=2, 30/66 pairs share the same basis
  → 45% of pairs have corr≈0.95 → median dominated by within-group pairs.

**v7** (K=3, λ∈[0, 0.06]):
- corr=0.062, top5=0.819, entropy=0.849, var=6.66
- With K=3, only 18/66 pairs (27%) share a basis → median shifts to cross-basis region
- entropy=0.849 hits the target range [0.85, 0.93] ✓

### 4.9 v8 — Increased λ + group_scale

**Config**: λ∈[0.01, 0.06], group_scale max_mean 12.0, min_mean 3.0

**Results**:
- corr=0.076, var=11.9 ✓, entropy=0.857 ✓, top5=0.852
- var and entropy hit targets. corr near (p75=0.103).

### 4.10 v9 (Current) — λ_min=0.02 + residual 0.5-2.0

**Config**: λ∈[0.02, 0.06], residual_sigma [0.5, 2.0], group_scale as v8, K=3

**Results**:
- var=12.5 ✓ (≥ 10)
- entropy=0.839 (near target 0.85, very close)
- corr=0.060 (p75=0.142 ✓ — 25% of tables hit target)
- top5=0.835 (structural, above target 0.65-0.75)

## 5. Failed and Abandoned Approaches

### 5.1 Continuum Basis Model (P2)
**What**: All basis vectors anchored to one global prototype with descending ρ_k.
**Why failed**: Made all projections too similar — inter-basis cosine ≈ 0.21 even at min ρ.
Pushed corr to 0.47 and top5 to 0.99 — extreme concentration.
**Lesson**: The continuum model violates the goal of SPREADING eigenvalues across components.

### 5.2 Per-Feature-Basis Perturbation (Random Noise)
**What**: `proj += pert · torch.randn(seq_len)` per feature per forward call.
**Why failed**: Perturbation noise was (a) non-deterministic (different each forward call),
and (b) too weak — even σ=0.6 barely dented within-group correlation from 0.96 to 0.95.
**Lesson**: To break rank-1 blocks, perturbation needs to be ~50% of signal magnitude
(σ≈1.5), which destabilizes the output too much.

### 5.3 Per-Feature-Basis Perturbation (Fixed Offset)
**What**: `proj += pert_j · row_norms` where pert_j is a fixed per-feature scalar.
**Why failed**: `row_norms` is the SAME for all features sharing a signal group. The
perturbation became `pert_j × common_signal` — perfectly correlated across features.
**Lesson**: Any perturbation that's collinear with the shared signal cannot differentiate
features within a group.

### 5.4 Column-Normalized Coupling W (P1)
**What**: Random low-rank W = U@V^T, column-normalized to unit norm.
**Why failed**: Columns had very different coupling profiles — some columns got strong
cross-family mixing while others got weak intra-family mixing. The MEDIAN correlation
didn't move even though some columns became extremely correlated.
**Lesson**: Uniform mixing (each column gets λ·mean(all others)) is simpler and more
predictable than random column-specific mixing profiles.

### 5.5 Inter-Family-Weighted Coupling W
**What**: W[k,j] = 2.0 if features k,j are in different families, 0.5 if same family.
**Why failed**: Small λ values (0.02) created large jumps in correlation (0.09→0.47)
because the weighted W amplifies the small existing cross-basis covariance from the
signal structure.
**Lesson**: Keep W uniform to avoid amplifying signal-structure artifacts.

## 6. Key Technical Discoveries

### 6.1 Signal Covariance Creates a Correlation Floor

Even with perfectly orthogonal basis vectors (Gram-Schmidt), projections through
the same signal have non-zero correlation because the SIGNAL ITSELF has structured
covariance:

```
Cov(proj₀, proj₁) = B₀^T Σ B₁
```

where Σ is the covariance matrix of the signal (e.g., Fourier basis functions are
mathematically correlated). The only way to make projections truly independent is
**subspace splitting**: each basis projects from a DISJOINT subset of signal dimensions.

### 6.2 DFS Dilution is a Feature Count Problem, Not a Structure Problem

When the 12 raw feature columns are expanded to 36 DFS columns (via relational feature
engineering), the ORIGINAL 12 columns' correlation structure is perfectly preserved.
But the median across ALL 36 columns drops because the 24 new columns are weakly
correlated (~0.05-0.09) with the original 12.

```
orig-orig pairs:  C(12,2) = 66   — high correlation (~0.15-0.50)
orig-new pairs:   12×24 = 288    — low correlation (~0.05)
new-new pairs:    C(24,2) = 276  — low correlation (~0.08)
────────────────────────────────
Total: 630 pairs → median dominated by low-corr majority
```

The raw-to-DFS median drop (0.18→0.05) is a mathematical artifact of adding weakly
correlated relational features, NOT a loss of original correlation structure.

### 6.3 Real Data Has SPREAD Eigen-Spectrum, Not Concentrated

The user's hypothesis was that real data has "少数主因子 + 长尾" (few dominant
factors + long tail). Testing on rel-event raw tables showed the OPPOSITE:

| | |corr| p50 | Top-5/Total | Entropy |
|---|:--:|:--:|:--:|
| Synthetic (K=3, subsp, λ=0) | 0.088 | 0.93 | 0.63 |
| Real (rel-event, 12-col subsample) | ~0.07 | ~0.67 | ~0.92 |

The real data's eigenvalue spectrum is MORE uniform (entropy 0.92 vs 0.63), with
correlation spread across many components rather than concentrated in a few. The
synthetic data's rank-deficient structure (12 features driven by 6-9 underlying
signals) creates a MORE concentrated spectrum than real data.

### 6.4 K Controls Median Correlation Structure

With K basis vectors per group and N features, the fraction of pairs sharing a basis
is approximately `C(N/K, 2) × K / C(N, 2)`. For the median to be in the cross-basis
region, this fraction must be < 50%:

| K | Pairs/group | Same-basis pairs | Cross-basis pairs | Median |
|:--|:-----------:|:----------------:|:-----------------:|:------:|
| 1 | 12 | 66 (100%) | 0 | within-group (→ 0.95) |
| 2 | 6 | 30 (45%) | 36 (55%) | ~cross-basis |
| 3 | 4 | 18 (27%) | 48 (73%) | cross-basis |
| 4 | 3 | 12 (18%) | 54 (82%) | cross-basis |

K=2 barely crosses the 50% threshold (within-group at 45%). K=3 is safer (27%).
With WEAK coupling (λ∈[0.02, 0.06]), the cross-basis correlation can be tuned
precisely to meet the target range [0.10, 0.14].

```python
residual_sigma: [0.5, 2.0]
```

### 7.2 Active Mechanisms

1. **Subspace-split orthogonal bases**: K=3 disjoint subspaces per group, Gram-Schmidt
   orthonormal. Guarantees zero cross-basis projection correlation.
2. **Round-robin basis allocation**: K=3 bases → 4 features per basis. Shared sign
   per (group, basis_idx) — features sharing a basis get identical projection direction.
3. **Uniform off-diagonal coupling**: `W = (1 - I)/(n-1)`. Each feature gets
   λ·mean(all other features). λ directly controls cross-basis correlation.
4. **Archetype-driven α**: Source tables get time-only, dependent tables split across
   time+parent+path based on table metadata.

### 7.3 Removed Mechanisms
- Continuum basis model (too concentrated)
- Per-feature-basis perturbation (ineffective at breaking rank-1 blocks)
- Inter-family-weighted coupling W (amplified signal-structure artifacts)

## 9. Remaining Gaps

### 9.1 Correlation Median Below Target

Current median 0.060 (target 0.10-0.14). The p75=0.142 shows 25% of tables are in range.
The issue is λ sampling: uniform distribution [0.02, 0.06] means most tables get λ<0.04
which gives corr<0.08 for dependent tables. A Beta distribution biased toward 0.03-0.05
would shift the median.

### 9.2 Eigen-Spectrum Too Concentrated

Current top5/total=0.835 (target 0.65-0.75). This is structural: K=3 × 4 features per
block = 3 rank-1 blocks dominating the eigenvalue spectrum. To fix:
- Increase K to 4 (divisor=2 → K=min(3,4)=3 — still K=3 due to the min(3,…) cap)
- Remove the `min(3, …)` cap: with divisor=2, time K=4, parent K=6, path K=4.
  Fewer features per basis → less concentration → lower top5.
- Or add per-feature basis-vector perturbation: for each feature j using basis k,
  use `B[k] + η·δ_{j,k}` where δ is a fixed per-feature-basis perturbation vector.

### 9.3 `num_basis_families` and `basis_family_rho` HPs are Dead Code

These were added for P2 (correlated basis families / continuum model) but are no longer
used after reverting to independent + subspace-split bases. They remain in the HP
dictionary but have no effect. Can be safely removed or kept for future experimentation.

# Cross-Table Feature Correlation: Journey of Two Failed Approaches

**Date**: 2026-05-24
**Branch**: `feature/hsbm-temporal-refactor`
**Status**: Both attempted approaches failed. Root causes identified. Path forward documented.

## 11. Problem Statement

Real relational datasets exhibit strong internal correlation among joined/aggregated columns (joined_corr ≈ 0.186 p50 in DFS-2 benchmark). This comes from:

1. Multiple aggregation functions (MEAN, STD, MAX, MIN) on the same parent column being mathematically linked
2. FK connections reflecting genuine entity relationships (collider bias): conditioning on an FK tuple induces correlation between otherwise-independent parent features

Our synthetic generation produced joined_corr ≈ 0.053 — a 3.5× gap vs real data.

### Baseline Metrics

| Metric | Real DFS-2 (p50) | Synthetic Baseline |
|--------|:---:|:---:|
| overall_corr | 0.083 | 0.036 |
| native_corr | 0.049 | 0.073 |
| joined_corr | 0.186 | 0.053 |
| cross_corr (A vs B parent) | 0.036 | 0.026 |

**Key observation**: Native correlation was already HIGHER than real data (0.073 vs 0.049). The signal-group feature generation worked for within-table correlation. The gap was entirely in joined-column correlation — features from DIFFERENT parent tables have ~0 cross-correlation because each parent uses an independent MLPSCM instance.

## 12. Attempt 1: FK Propensity Matching (FAILED)

### 12.1 Design

1. Per-parent: percentile-rank each row by a random linear combination of 2-3 feature columns → `rank_score[a] ∈ [0, 1]`
2. Per-child row: sample a shared latent `z(j) ~ Uniform(0,1)`, then per-parent propensity target `t_p(j) = ρ·z(j) + √(1-ρ²)·ε_p(j)`
3. Within each HSBM block, re-weight FK sampling probabilities by `exp(-β·|rank_score[a] - t(j)|)` — bias toward parent rows whose rank matches the child's propensity target

**Intended mechanism**: shared `z(j)` → correlated propensity targets across parents → correlated rank selections → correlated feature values.

### 12.2 Implementation

- ~330 lines added to `hsbm.py` (4 new functions: `_compute_rank_scores`, `_sample_fk_per_parent_with_propensity`, `compute_hsbm_fk_ids_with_propensity`, `compute_hsbm_fk_ids_multi_with_propensity`)
- 4 new HPs in `prior_config.py`
- Propensity branching in `_compute_hsbm_fk_ids()` in `table_generation.py`

### 12.3 Results (64 RDBs)

| Metric | Baseline | v1 (ρ 0.05-0.20) | v2 (multi ρ 0.40-0.70) |
|--------|:---:|:---:|:---:|
| joined_corr (all) | 0.053 | 0.076 | 0.060 |
| joined_corr (single-parent) | — | 0.116 | 0.081 |
| joined_corr (multi-parent) | — | 0.045 | 0.047 |
| cross_parent (A vs B) | 0.026 | 0.032 | 0.029 |

Single-parent uplift (0.053→0.081) confirmed but multi-parent **unchanged** (0.045-0.047 vs 0.053 baseline). Overall improvement concentrated entirely in single-parent tasks where no cross-parent correlation is needed.

### 12.4 Root Cause

**Rank function is a per-parent random linear combo of independent SCM features.** Each parent A and parent B compute `rank_score[a]` from different random linear combinations of different feature spaces. Even when shared `z(j)` forces all parents to target the same percentile (e.g., 0.7), the underlying feature vectors at that percentile are unrelated:

```
Parent A, rank 0.7 row: [feature_0=2.3, feature_1=-0.5, ...]
Parent B, rank 0.7 row: [feature_0=-1.1, feature_1=3.7, ...]
```

These feature vectors have zero expected correlation. The ranking axis is not shared across parents, and there is no structural relationship between what "0.7" means in parent A vs parent B.

### 12.5 Lessons

1. **Aligning ranks ≠ aligning features.** Ranks are a 1D projection of a D-dimensional feature vector. D-1 degrees of freedom remain independent and dominate the correlation statistics.
2. **Post-sampling re-weighting can't inject content.** Propensity changes WHICH parent row is selected but doesn't change WHAT the parent features are. Correlation requires shared CONTENT, not shared selection.
3. **Single-parent improvement was illusory.** The uplift came from within-table variance reduction (biased FK toward feature outliers within a single parent), not from genuine cross-table correlation. Multi-parent tasks — the actual target — showed zero improvement.
4. **Multi-parent is the hard problem.** Any approach that only shows single-parent improvement is not solving the right thing. Cross-parent correlation requires information to flow BETWEEN independent generation processes.

## 13. Attempt 2: Structural Signature Injection (FAILED)

### 13.1 Design

Different paradigm: instead of modifying FK sampling (which rows connect), modify parent FEATURES post-hoc (what those rows contain).

1. After ALL FKs are determined (post-topological loop), compute per-parent-row structural signatures from the FK graph
2. Blend signatures into random float columns of parent features: `X_new[:, col] = (1-α)·X_old[:, col] + α·sig[idx]`
3. 4 signature dimensions:
   - sig_1: `log(1+deg) / log(1+max_deg)` — in-degree ratio
   - sig_2: `H(child_table, fk_col) / H_max` — reference entropy over (child_table, FK_position) pairs
   - sig_3: `log1p(distinct_co_parents) / log1p(table_max)` — co-parent diversity
   - sig_4: `ref_count / active_time_window` — temporal density

**Intended mechanism**: parent rows that frequently co-occur in multi-parent children → both get high `co_parent_diversity` → both have feature columns shifted by the same structural signal → child tasks see correlated feature values after join.

**Key argument**: signature is computed FROM the FK structure itself, not from random feature projections. Feed-forward injection, not sampling-time re-ranking.

### 13.2 Implementation

- New file: `src/prior/struct_sig.py` (270 lines) with `compute_structural_signatures(rdb)` and `inject_signatures_into_parents(rdb)`
- Pipeline hook in `generate_all_data_from_SCM()` after topological loop, before materialize
- 3 HPs: `struct_sig_active` (always True), `struct_sig_dims` ∈ {2,3,4}, `struct_sig_alpha` ∈ [0.65, 0.90]
- Z-score normalization: signature normalized per-column to match target column's mean and std before blending
- Only DataType.FLOAT columns modified (skip CATEGORICAL, BINNED)
- ~330 lines of FK propensity code removed from `hsbm.py` (594→263 lines)

### 13.3 Results (64 RDBs)

| Metric | Baseline | FK Propensity | **Struct Sig** |
|--------|:---:|:---:|:---:|
| joined_corr (all) | 0.053 | 0.060 | **0.047** |
| joined_corr (single-parent) | — | 0.081 | **0.059** |
| joined_corr (multi-parent) | — | 0.047 | **0.037** |
| cross_parent (A vs B) | 0.026 | 0.029 | **0.027** |

**Worse than baseline on every metric.** The injection mechanism was verified working at the code level (standalone test confirmed parent feature values changed, only referenced parents modified), but the effect on correlation is undetectable.

### 13.4 Root Cause: Signal Dilution

The structural signal is too mathematically weak to measurably affect correlation statistics.

**Quantitative analysis for a typical multi-parent child:**

For parent A (10 float features) and parent B (10 float features):
- Only `f = 0.3` (3 out of 10) feature columns are modified per parent
- Only 1/3 of the sig dimensions (co_parent_diversity) contributes to cross-parent correlation
- Blend weight α ≈ 0.8

The cross-parent correlation contribution from sig injection:
```
Δcorr ≈ f² · α² · corr(S_A, S_B) / ((1-α)² + α²)
```
With f=0.3, α=0.8, corr(S_A, S_B) ≈ 0.3 (estimated structural similarity):
```
Δcorr ≈ 0.09 · 0.64 · 0.3 / 0.68 ≈ 0.025
```

This is the theoretical MAXIMUM in ideal conditions. In practice:
- corr(S_A, S_B) is closer to 0.1 due to row-level vs pair-level mismatch (see §13.5)
- Feature pairs between UNMODIFIED columns (70% of pairs) carry zero sig-based correlation
- The 30% modified × 30% modified = 9% of cross-parent feature pairs actually carry signal
- Median correlation across ALL pairs barely moves

### 13.5 Secondary Issue: Row-Level vs Pair-Level Signal

`co_parent_diversity` is a **row-level property**: it measures how many distinct other-parent tables co-occur with parent row `i`. It does NOT measure the affinity between a specific parent_A row `i` and parent_B row `j`.

If parent_A.row[5] has high co_parent_diversity (frequently in multi-parent children), ALL child rows referencing parent_A.row[5] see the SAME high value — regardless of which specific parent_B row they join with. The signal has zero **pair-level variation**.

For correlation to emerge, feature values must vary AT THE CHILD ROW LEVEL in a way that aligns across parents. Row-level injection into parent features is inherently limited because:

- Parent row features are shared by ALL children referencing that row
- The structural signal is constant across all FK pairs involving the same parent row
- Only pair-level signal variation produces detectable cross-parent correlation: corr(X, Y) depends on (x_i, y_i) PAIRS, not on x_i and y_j independently

### 13.6 Lessons

1. **Signal coverage matters more than signal design.** Modifying `f` fraction of columns dilutes cross-parent correlation by `f²`. Even with a perfect signal (corr=1.0 between S_A and S_B), modifying 3/10 columns gives at most `f² ≈ 0.09` contribution to the overall cross-parent correlation — barely above noise.

2. **Row-level injection is pair-level blind.** A structural signature that varies per parent row but is constant across all child rows referencing that row cannot create pair-specific correlation patterns. The correlation structure must exist in the JOINT distribution of (parent_A_feat, parent_B_feat) pairs, not in the marginals.

3. **Z-score normalization doesn't fix the variance reduction.** Normalizing signatures to match per-column statistics preserves column-level mean and std, but the blend `(1-α)·X + α·S` reduces feature variance by a factor of `(1-α)² + α² ≈ 0.68` for α=0.8. The injected signal's cross-parent covariance `α²·Cov(S_A, S_B)` must overcome not just the original noise but also this variance shrinkage.

4. **Feed-forward injection suffers from the same information bottleneck as sampling-time re-ranking.** Both approaches try to inject structural information through a narrow channel (FK sampling probability in propensity, a few feature columns in struct_sig) that is too thin to carry enough signal for statistical detection across hundreds of feature pairs.

5. **The estimation model was too optimistic.** The expected bound in `findings.md` assumed:
   ```
   baseline + α · (sig_dims/total_features) · struct_sim ≈ 0.08
   ```
   This uses `f` not `f²`, missing the fundamental fact that cross-parent correlation requires BOTH parent A's features AND parent B's features to carry the signal. The correct formula is `baseline + f²α²·corr(S_A, S_B)`, which is an order of magnitude smaller.

## 14. Architectural Insight: Why Both Approaches Failed

### 14.1 The Shared Flaw

Both approaches share the same fundamental assumption: **structural information can be injected through a narrow, existing channel** in the generation pipeline.

| Approach | Channel | Why it's too narrow |
|----------|---------|---------------------|
| FK Propensity | FK sampling probability | Only changes WHICH row is selected; features are generated independently per parent beforehand |
| Struct Sig | Post-hoc feature blending | Only modifies a small fraction of feature dimensions; pair-level variation is zero |

### 14.2 The Fundamental Tension

```
Real data:  Entity state → FK relationships + Feature values (jointly determined)
Synthetic:  Feature values → FK relationships (sequential, decoupled)
```

In synthetic generation, each parent table's SCM runs independently. Parent A's features are generated without any knowledge of which parent_B rows they'll be joined with. Two decoupled processes produce rows that are then randomly assigned FK connections via HSBM:

```
SCM_A(seed_A) → features_A    }  independently generated
SCM_B(seed_B) → features_B    }
                                         → HSBM → FK assignment
```

The FK is a post-hoc label, not a causal determinant. In real data, the FK structure and feature values are JOINTLY determined by the underlying entity state (e.g., a customer's wealth tier simultaneously affects which orders they place AND their demographic features).

### 14.3 The Information Bottleneck

Any attempt to inject cross-parent correlation after feature generation faces the same bottleneck: the only channels available are:

1. **FK sampling** (which parent rows connect to which child rows) — already occupied by HSBM for structural realism
2. **Feature values** (what those parent rows contain) — already determined by MLPSCM for within-table structure

Both channels are "narrow" in the sense that their primary function constrains how much additional information they can carry. The FK sampling channel can only re-rank within HSBM blocks without destroying the block structure. The feature blending channel can only modify a few columns without destroying the intra-table correlation structure.

## 15. What Might Actually Work

### 15.1 Option A: Joint Parent Feature Generation (FK-First)

Instead of generating each parent's features independently and then assigning FKs, jointly generate parent features CONDITIONED on the FK structure:

- After FK structure is determined, generate parent features such that rows connected to the same children share latent components
- This requires inverting the generation order: FK first, then features conditioned on FK
- Challenge: topological order requires parent features to exist before children can be generated (the child SCM takes parent features as input). This creates a circular dependency.

### 15.2 Option B: Child-Level Structural Noise Injection

Inject a shared noise component into the child SCM's parent-feature processing step:

- For multi-parent children, sample a shared latent vector per child row
- This latent modulates how parent features are combined/transformed in the child SCM
- The modulation creates correlation among the child's parent-derived features without modifying parent tables
- This is pair-level injection (varies per child row, which IS a specific FK pair)

### 15.3 Option C: Shared Archetype Priors Across Parents

Modify the signal-group feature generation to share archetype basis components across parents linked by FK relationships:

- If parent A and parent B both have FK connections to child C, they share a subset of archetype bases
- The shared bases create genuine feature correlation across parent tables at generation time
- This addresses the ROOT CAUSE (independent SCMs) rather than patching the output
- Most architecturally clean approach: the correlation is endogenous, not injected

### 15.4 Option D: Acknowledge the Gap as Structural

The joined_corr gap (0.053 vs 0.186) is partly explained by real data's aggregation mechanism — multiple aggregation functions on the same column are mathematically linked. Our complex tasks use direct FK joins, not aggregations. A more realistic target accounting for this structural difference:

- joined_corr target: ~0.08-0.10 (achievable through collider bias alone, without aggregation artifacts)
- This still requires shared archetype priors (Option C) to achieve

| # | Approach | Problem | Key Flaw | Lesson |
|---|----------|---------|----------|--------|
| 1 | Continuum basis model | Feature correlation within tables | Made all projections too similar (corr=0.47) | Shared prototype creates extreme concentration |
| 2 | Per-feature-basis perturbation (random) | Within-table feature correlation | Non-deterministic, too weak | Need ~50% signal magnitude to break rank-1 blocks |
| 3 | Per-feature-basis perturbation (fixed) | Within-table feature correlation | Collinear with shared signal | Any shared-signal-aligned perturbation is perfectly correlated |
| 4 | Column-normalized coupling W | Within-table feature correlation | Column-specific profiles unpredictable | Uniform mixing is simpler and more predictable |
| 5 | Inter-family-weighted coupling W | Within-table feature correlation | Amplified signal-structure artifacts | Keep W uniform to avoid amplifying covariance artifacts |
| 6 | FK Propensity Matching | Cross-table feature correlation | Rank aligns ranks, not features | 1D projection can't inject D-dimensional structure |
| 7 | Structural Signature Injection | Cross-table feature correlation | Signal dilution + row-level blindness | f² scaling + pair-level mismatch makes signal undetectable |

## 17. Meta-Lessons

1. **Always derive the effect size formula before implementing.** For FK propensity, a simple derivation would have shown that `corr(rank_A[i], rank_B[j])` is unrelated to `corr(feature_A[i], feature_B[j])`. For struct_sig, the `f²` dilution factor was overlooked in the initial estimation (which used `f` instead of `f²`).

2. **Test on the hardest case first (multi-parent).** FK propensity showed uplift on single-parent (0.053→0.081) which created false confidence. The multi-parent result (0.047, unchanged) was the true signal. Single-parent correlation can be improved by many mechanisms that don't help cross-parent correlation.

3. **Row-level interventions can't create pair-level structure.** Both approaches tried to inject structure at the wrong level of granularity. FK propensity operates at the row-sampling level; struct_sig operates at the row-feature level. Cross-parent correlation exists at the PAIR level (which specific parent_A row connects to which specific parent_B row).

4. **Post-hoc injection faces fundamental information-theoretic limits.** Once features are generated independently, any post-hoc modification can at best add `O(f²α²)` additional correlation, where `f` is the fraction of features modified. With realistic `f ≈ 0.3, α ≈ 0.8`, this is `≈ 0.06` — barely above noise. To be effective, correlation must be ENDOGENOUS to the generation process.

5. **Write the journey.** If we had documented the FK propensity failure analysis completely before pivoting to struct_sig, we might have caught the shared architectural flaw earlier. The `f²` dilution issue in struct_sig is structurally analogous to the "1D projection can't capture D-dimensional structure" issue in propensity.

### 18.6 Lessons

1. **Shared projection (W matrix) is necessary but not sufficient for cross-parent correlation.** It makes FK targets comparable across parents, but the features being joined are still independently generated. The matching latent biases which rows are paired but does not change feature values.
2. **FK sampling bias has a hard upper bound on cross_corr.** Even with perfect matching (FK pairs always choose parent rows with identical latent projections), `corr(parent_A_feat[a], parent_B_feat[b]) ≈ 0` because the feature vectors are generated by independent MLPSCM instances.
3. **The next step must be generation-time coupling (§15.3 Shared Archetype Priors).** As long as parent_A and parent_B features are generated by independent SCMs, no post-hoc FK intervention can create substantial cross-parent feature correlation. The shared basis sub-component must be IN the features at generation time, not added afterward.
4. **Task-level vs H5-level eval produces different absolute values** but consistent deltas. Task-level eval preserves column type distinctions (native/joined/aggregated) which H5-level subsampling obscures.
