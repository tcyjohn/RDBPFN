# Entity Temporal Snapshots + Same-Entity Bias Design

**Date**: 2026-06-08
**Status**: Approved

## Motivation

### Gap 1: Entity table structure mismatch with real benchmarks

Real benchmark entity tables (rel-amazon-dfs-2, rel-stack-dfs-2, amazon-dfs-2):
- Multiple rows per entity (temporal snapshots)
- 100% have timestamp columns
- Same entity appears at multiple time points in the same task

Current synthetic generation:
- Entity tables: one row per entity
- Entity tables: never have timestamps (`entity_prob=0.0`)
- This contradicts all real benchmarks

### Gap 2: Root entity has no HSBM structural signal

- Homophily labels for root entities use pseudo-blocks (feature clustering), NOT HSBM blocks
- FK bias only works for child tables (sibling clustering), not for root entities
- Root entities make up ~80% of task tables in relbench_mode

### Gap 3: No same-entity temporal self-connection in flat PFN sequence

- PFN flattens the relational graph into a DFS sequence
- Multiple rows of the same entity are just "rows" in the sequence
- No mechanism to tell the model "these two rows are the same entity at different times"

## Design

### 1. Entity Table Temporal Snapshots (Generation)

**New parameters**:
- `snapshots_per_entity_range`: random integer range (e.g., [5, 20]), sampled per entity table
  - Entity table total rows = `num_entities (DAG) × snapshots_per_entity`
- `entity_timestamp_prob`: float (default 1.0), probability an entity table gets a timestamp column
- Entity PK column: deterministic, shared across all snapshots of same entity

**Entity table schema**:
```
Entity: num_entities × snapshots_per_entity rows
  - entity_pk: [0, 1, ..., num_entities-1] (repeated per snapshot)
  - timestamp:  sampled via TemporalVocab (same mechanism as activity tables)
  - features:   generated by SCM with timestamp signal
```

**Timestamp signal**: Same TemporalVocab mechanism as activity tables (8-dim Fourier basis + 3-dim gate → MLP). Entity timestamps are independently sampled per snapshot, no temporal ordering constraints needed.

### 2. HSBM Block Assignment (cluster_a Storage)

**Current state**: `cluster_a` (parent-side blocks) is computed in `compute_hsbm_fk_ids()` but discarded — only `cluster_b` (child-side) is returned.

**Change**: All HSBM FK functions return `cluster_a` as well:
- `compute_hsbm_fk_ids()` → `(fk_ids, cluster_b, cluster_a)`
- `compute_hsbm_fk_ids_multi()` → same
- `compute_hsbm_fk_ids_multi_with_matching()` → same

**Storage**: `cluster_a` stored as `hsbm_parent_blocks` on the parent table's TableGenerator, collected on RDB per table.

### 3. Entity-Level Block Consistency (New Constraint)

**Problem**: `assign_cluster_at_levels()` assigns blocks by row index. With temporal snapshots, different rows of the same entity could get different blocks → label inconsistency.

**Fix**: Block assignment operates on unique entities, then broadcasts to snapshots:

```
unique_entity_ids = range(num_entities)
cluster_per_entity = assign_cluster_at_levels(num_entities, hierarchy)
cluster_per_row = cluster_per_entity[entity_id[row]]  # broadcast
```

This guarantees: same entity_id → same block → same label across all snapshots.

**Note**: Neither current RDBPFN nor plurel handle this — it's a new constraint introduced by entity temporal snapshots.

### 4. Homophily Block Assignment Priority

`get_block_assignments(target_table)` checks in this order:

```
1. hsbm_block_paths[target_table]     ← cluster_b (entity as child, aligns with OPENRFM)
2. hsbm_parent_blocks[target_table]   ← cluster_a (entity as parent, root entity fallback)
3. pseudo-blocks                      ← feature clustering (last resort)
```

**Rationale**: OPENRFM's `b_parent % 2` uses child-side blocks (cluster_b). Non-root entities use path 1 (matches OPENRFM exactly). Root entities use path 2 (HSBM parent block, genuine structural signal replacing pseudo-blocks).

### 5. Same-Entity Attention Bias (Model)

**Formula**: `I[entity_id[i] == entity_id[j]] * λ_se`

- `entity_id`: entity PK value, -1 for non-entity rows (padding)
- `λ_se`: per-layer learnable scalar, softplus-constrained to be positive

**Integration**: Combined with FK bias:
```
total_bias = fk_bias + entity_bias
```
Both added to `attn_mask` in `TransformerEncoderLayer.forward()`.

### 6. H5 Data Format

New H5 dataset alongside existing `fk_values`:
- `entity_ids`: (num_samples, max_rows) int64, -1 pad
- `entity_id_column_name`: H5 attr (metadata)

### 7. Eval Integration

Real benchmarks naturally have entity PK columns:
- rel-amazon-dfs-2: `customer_id`, `product_id`
- rel-stack-dfs-2: `Id` (users table)
- amazon-dfs-2: `customer_id`, `product_id`

`load_task_split()` detects entity PK from metadata, returns alongside FK values.

### 8. Priority Sampling (Training)

Dataloader-level: when building batches, prioritize including at least 2 temporal snapshots of the same entity per batch. This ensures same-entity bias receives gradient signal.

Detail deferred to Phase 7 implementation.

## Bias Summary

| Bias | Formula | Purpose | Effective on root entity |
|---|---|---|---|
| FK bias | `I[fk[i]==fk[j]] * λ_fk` | Child siblings share attention | NO |
| Same-entity bias | `I[eid[i]==eid[j]] * λ_se` | Same entity across time | YES |
